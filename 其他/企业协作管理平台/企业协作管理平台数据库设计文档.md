## 7.核心数据表含义总览

| 表名                         | 该表代表的实体和说明                                                                               |
| -------------------------- | ---------------------------------------------------------------------------------------- |
| `tenant`                   | **租户 / 企业**。代表入驻系统的一家公司，是整个多租户系统中的核心顶层业务实体。后续部门、员工、公告、审批、聊天等数据，基本都会挂在某个租户下面。             |
| `account`                  | **登录账号**。代表“谁可以登录系统”。它是统一身份主体，不直接等同于员工，因为一个账号理论上可以加入多个租户。                                |
| `tenant_member`            | **租户成员 / 企业成员身份**。代表“某个账号在某个企业中的成员身份”。这是连接 `account` 和 `tenant` 的中间实体，表示这个人在哪家公司任职。      |
| `department`               | **部门**。代表企业内部的组织单元，如总经办、研发部、人事部、财务部等。支持树形结构，用于组织架构展示和数据权限范围划分。                           |
| `position`                 | **职位 / 岗位**。代表企业中的岗位定义，如前端工程师、HR 专员、部门经理等。它偏向岗位模板，而不是具体某个人。                              |
| `employee_profile`         | **员工档案**。代表企业成员的详细业务资料，是 `tenant_member` 的补充信息，如姓名、头像、联系方式、所属部门、职位等。可以理解为“成员身份的员工信息扩展表”。 |
| `reporting_line`           | **汇报关系**。代表员工之间的上下级关系，比如 A 直接汇报给 B。它不只是组织展示用，也会影响审批流、数据权限和管理权限。                          |
| `role`                     | **角色**。代表一组权限集合的抽象身份，如平台管理员、企业管理员、普通员工、HR、审批管理员等。                                        |
| `permission`               | **权限点**。代表系统中的一个具体操作许可，如“创建公告”“查看员工信息”“审批申请”“管理部门”。它是权限体系里的最小操作单元。                       |
| `role_permission`          | **角色-权限关系**。代表某个角色拥有哪些权限点。它本质上是 RBAC 中“角色”和“权限”之间的关联表。                                   |
| `member_role`              | **成员-角色关系**。代表某个企业成员被授予了哪些角色。例如某个成员被赋予“部门管理员”或“审批管理员”角色。                                 |
| `notice`                   | **公告**。代表企业内发布的一条公告信息，比如公司通知、制度更新、节日放假通知等。                                               |
| `notice_target`            | **公告投放范围**。代表一条公告发给谁。它解决“公告是发给全员、某部门、某角色，还是某几个指定成员”的问题。                                  |
| `notice_read`              | **公告阅读记录**。代表“谁在什么时间读过哪条公告”，用于已读未读统计。                                                    |
| `approval_template`        | **审批模板**。代表一类审批表单定义，如请假申请、报销申请、出差申请。它解决“审批长什么样、有哪些字段”的问题。                                |
| `approval_flow`            | **审批流程定义**。代表某个审批模板对应的流程版本，例如请假审批需要“直属领导审批 → HR 审批”。它是审批规则本身。                            |
| `approval_flow_node`       | **审批流程节点**。代表审批流程中的某一步，如第 1 步直属上级审批、第 2 步财务审批。                                           |
| `approval_instance`        | **审批实例 / 审批单**。代表某一次真实发起的审批申请。例如“张三在 2026-03-18 发起了一条请假申请”。它是运行中的具体业务单据。                 |
| `approval_task`            | **审批任务**。代表审批流程流转到某个审批人时，系统生成的一条待办任务。比如“李经理现在有一条待审批的请假申请”。                               |
| `notification`             | **通知**。代表系统发给某个成员的一条消息提醒，比如审批提醒、公告提醒、系统提醒。它是统一通知中心的核心表。                                  |
| `chat_conversation`        | **聊天会话**。代表一个聊天对象容器，可以是一对一单聊，也可以是群聊。                                                     |
| `chat_conversation_member` | **会话成员**。代表哪些成员属于某个聊天会话。比如某个群里有哪些人，或者某个单聊里有哪两个人。                                         |
| `chat_message`             | **聊天消息**。代表会话中的一条具体消息，如文本、图片、文件、系统消息等。                                                   |
| `chat_read_cursor`         | **聊天阅读游标 / 已读位置**。代表某个成员在某个会话中已经读到了哪一条消息，用于未读数和已读状态计算。                                   |
| `audit_log`                | **审计日志**。代表系统中重要操作的留痕记录，比如谁修改了角色权限、谁删除了公告、谁审批了某条申请。它用于审计、追责和问题排查。                        |

# 三、数据库约束与业务约束实施原则（按当前项目要求修订）

结合当前企业协作管理平台的设计要求，数据库建模阶段采用以下原则：

## 总体原则

本项目当前阶段对数据库约束采取 **“弱数据库约束、强业务层约束”** 的策略：

- **数据库层仅保留主键约束（PK）与非空约束（NOT NULL）**
    
- **除主键和非空外，其他约束原则上不在数据库层强制实现**
    
- **外键约束、唯一约束、默认值控制、枚举值限制、删除策略、复杂一致性校验、权限控制等，统一放在代码业务层实现**
    
- 这样做的主要目的是：
    
    - 降低数据库层耦合度
        
    - 提高后续模型调整和迭代灵活性
        
    - 便于 AI 在代码层统一实现业务校验逻辑
        
    - 避免数据库层约束与业务层规则重复维护
        

---

# 四、数据库层保留的约束

当前数据库层仅建议保留以下两类约束：

## 1. 主键约束

适用于所有核心表：

- 每张表保留 `id` 作为主键
    
- 主键类型建议统一使用 `bigint`
    
- 主键生成策略可后续统一确定为：
    
    - 数据库自增
        
    - 雪花 ID
        
    - 或其他统一 ID 方案
        

### 设计要求

- 所有业务表必须有明确主键
    
- 主键仅用于唯一标识一条记录
    
- 不依赖数据库层的其他唯一约束来表达业务唯一性
    

---

## 2. 非空约束

仅对当前阶段明确不可为空的关键字段使用 `NOT NULL` 约束。

适用范围建议包括：

- 主键字段
    
- 关键名称字段
    
- 核心状态字段
    
- 创建时间字段
    
- 明确必须存在的业务字段
    
- 当前阶段已确定必须存在的关联 ID 字段
    

### 示例

如：

- `tenant.name`
    
- `account.password_hash`
    
- `tenant_member.tenant_id`
    
- `tenant_member.account_id`
    
- `role.scope_type`
    
- `permission.permission_code`
    
- `notice.title`
    
- `approval_instance.tenant_id`
    
- `chat_message.conversation_id`
    

### 说明

- 非空约束用于保证最基础的数据完整性
    
- 非空仅表达“字段必须有值”
    
- 不表达该值是否有效、是否属于正确租户、是否满足业务规则
    

---

# 五、不在数据库层实现的约束（统一放在代码业务层）

除主键和非空约束外，以下内容 **不在数据库层强制实现**，统一由代码业务层负责：

## 1. 外键约束

当前阶段不在数据库层建立 FK。

例如以下关系：

- `tenant_member.tenant_id -> tenant.id`
    
- `tenant_member.account_id -> account.id`
    
- `employee_profile.tenant_member_id -> tenant_member.id`
    
- `department.parent_id -> department.id`
    
- `member_role.role_id -> role.id`
    
- `notice.publisher_member_id -> tenant_member.id`
    
- `approval_instance.flow_id -> approval_flow.id`
    
- `chat_message.conversation_id -> chat_conversation.id`
    

以上关系仅作为 **逻辑关联关系** 存在，在代码层进行校验。

### 原因

- 多租户系统中，单纯数据库 FK 不能完整表达业务归属关系
    
- 后续迁移、导入、批处理、初始化数据更灵活
    
- 避免数据库层过度耦合导致后期改模型困难
    

### 代码层要求

业务层必须负责校验：

- 引用对象是否存在
    
- 是否属于同一租户
    
- 是否处于允许被引用的状态
    
- 是否满足当前上下文的访问条件
    

---

## 2. 唯一约束

当前阶段不在数据库层建立 UNIQUE 约束。

例如以下唯一性需求：

- `tenant.tenant_code`
    
- `account.username`
    
- `account.phone`
    
- `account.email`
    
- `(tenant_id, account_id)`
    
- `(role_id, permission_id)`
    
- `(tenant_member_id, role_id)`
    
- `(notice_id, tenant_member_id)`
    
- `(conversation_id, tenant_member_id)`
    

以上规则统一在代码层实现。

### 代码层要求

业务层必须显式处理：

- 新增前查重
    
- 更新前排重
    
- 并发写入下的重复提交控制
    
- 必要时通过事务、乐观锁、幂等机制保证一致性
    

### 说明

虽然唯一约束通常适合数据库层，但基于你当前要求，后续实现时应明确告诉 AI：  
**所有业务唯一性都在服务层判断，不依赖数据库 UNIQUE 约束。**

---

## 3. 默认值

当前阶段不强依赖数据库默认值。

例如：

- `status = 'active'`
    
- `created_at = now()`
    
- `updated_at = now()`
    
- `is_read = false`
    
- `sort_order = 0`
    

这些默认逻辑建议统一由代码层赋值。

### 代码层要求

- 所有创建逻辑在 service 层或 ORM model 层显式填充默认值
    
- 避免依赖数据库默认值与业务层默认值不一致
    
- 保证 AI 生成代码时默认行为清晰、集中、可测试
    

---

## 4. CHECK 约束 / 枚举值限制

当前阶段不在数据库层建立 CHECK 或 ENUM 约束。

例如：

- `status` 值域限制
    
- `conversation_type` 值域限制
    
- `message_type` 值域限制
    
- `scope_type` 值域限制
    
- `node_order > 0`
    
- `sort_order >= 0`
    

统一由代码层完成校验。

### 代码层要求

- 在 Pydantic / DTO / Schema 层做输入校验
    
- 在 service 层做业务兜底校验
    
- 枚举统一使用代码常量、Enum 类或配置中心定义
    
- 非法状态值不得写入数据库
    

---

## 5. 索引策略

当前阶段数据库设计文档中不将索引视为强制数据库约束项。

索引是否建立、建立哪些索引，应由后续：

- 查询路径设计
    
- 实际接口性能需求
    
- SQL 执行计划
    
- 压测结果
    

来决定。

### 当前原则

- 索引属于性能优化手段，不属于当前版本的强业务约束
    
- 不在本版文档中将其作为“必须落库”的硬性规则
    
- 后续进入 SQL 优化阶段再专项补充索引方案
    

---

## 6. 删除策略

当前阶段不在数据库层通过 FK 级联、约束删除规则等方式强制实现删除策略。

例如：

- 不使用 `ON DELETE CASCADE`
    
- 不通过数据库层级联规则控制关系删除
    
- 不通过数据库约束阻止历史表删除
    

统一由代码业务层控制删除行为。

### 代码层要求

业务层必须明确区分：

- 可物理删除的数据
    
- 不可物理删除的数据
    
- 应改为停用的数据
    
- 应使用软删除的数据
    

例如：

- 角色权限关系可按业务决定是否删除
    
- 历史审批、聊天消息、审计日志通常不允许随意物理删除
    
- 删除前必须经过业务校验与权限校验
    

---

# 六、代码层约束建议汇总（作为后续实现的核心要求）

由于数据库层仅保留主键与非空约束，因此以下规则必须在 **代码业务层** 完整实现。

## 1. 多租户隔离与数据归属校验

代码层必须强制实现：

- 当前登录人只能访问当前租户数据
    
- 所有跨表引用必须校验租户归属一致性
    
- `notice.publisher_member_id` 必须属于对应 `tenant_id`
    
- 审批任务处理人与审批实例必须属于同一租户
    
- 聊天成员、聊天会话、聊天消息必须属于同一租户
    
- 平台级角色与租户级角色必须严格区分作用域
    

### 说明

这是当前系统最核心的业务约束之一，不能依赖数据库结构自动保证。

---

## 2. 关联对象存在性校验

由于不使用外键约束，因此业务层必须显式校验：

- 新增或更新时，关联 ID 是否真实存在
    
- 被引用对象是否已删除、停用、失效
    
- 关联对象是否允许当前场景引用
    
- 父子节点关系是否合法
    

例如：

- 创建成员前校验租户和账号存在
    
- 创建员工档案前校验成员存在
    
- 创建审批实例前校验模板和流程存在
    
- 写入聊天消息前校验会话存在且发送人属于该会话
    

---

## 3. 唯一性校验

由于不使用数据库 UNIQUE，因此代码层必须负责：

- 登录标识唯一性校验
    
- 业务编码唯一性校验
    
- 关系去重校验
    
- 已读记录去重校验
    
- 成员角色去重校验
    
- 会话成员去重校验
    

### 示例

包括但不限于：

- 租户编码不能重复
    
- 用户名/手机号/邮箱不能重复
    
- 同一租户内同一账号不能重复加入
    
- 同一成员不能重复绑定同一角色
    
- 同一公告不能重复记录同一用户的已读状态
    

### 实现建议

- service 层写入前先查重
    
- 高并发场景增加幂等键或业务锁
    
- 必要时在应用层增加重复提交保护
    

---

## 4. 权限校验

系统采用 RBAC + 数据权限 + PyCasbin 思路，以下全部由代码层负责：

- 谁能访问总后台
    
- 谁能访问公司管理后台
    
- 谁能访问员工端
    
- 谁能创建公告
    
- 谁能分配角色
    
- 谁能管理部门
    
- 谁能查看审批单
    
- 谁能处理审批任务
    
- 谁能查看员工信息
    
- 谁能访问平台级资源
    
- 谁能访问租户级资源
    

### 说明

权限不是表结构问题，而是服务层和权限层的业务决策问题。

---

## 5. 数据范围控制

代码层必须实现：

- 仅本人可见
    
- 本部门可见
    
- 本部门及子部门可见
    
- 指定角色可见
    
- 全租户可见
    
- 平台管理员跨租户可见
    

### 适用模块

- 员工资料
    
- 审批单据
    
- 公告范围
    
- 通知范围
    
- 后台管理列表
    
- 审计日志查看范围
    

---

## 6. 状态流转规则

所有状态机规则统一在代码层实现。

例如：

- 草稿公告才能发布
    
- 已发布公告不能直接编辑核心内容
    
- 已撤回公告不能重复发布
    
- 审批单必须按节点推进
    
- 已完成审批不能再次审批
    
- 已退出群聊成员不能继续发送消息
    
- 停用成员不能再被指派审批任务
    
- 停用角色不能继续授予成员
    

---

## 7. 跨表复杂一致性校验

代码层必须承担以下复杂关系校验：

- 部门负责人必须属于本租户
    
- 部门父级不能指向自己或自己的下级
    
- 汇报关系不能形成环
    
- 审批节点中的 `approver_type` 与 `approver_ref_id` 必须匹配
    
- 单聊会话必须恰好两名成员
    
- 群聊成员必须属于同一租户
    
- 审批发起人不能审批自己的申请
    
- 公告投放对象必须匹配正确的目标类型
    
- 角色分配必须满足角色作用域要求
    

---

## 8. 审计与业务事件驱动逻辑

代码层负责记录和驱动：

- 谁创建了什么数据
    
- 谁修改了角色与权限
    
- 谁发起、审批、拒绝了审批
    
- 公告发布后自动创建通知
    
- 审批状态变化后自动推送通知
    
- IM 消息写入后自动更新未读状态
    
- 关键操作写入审计日志
    

---

## 9. 时间字段与默认字段填充

由于不依赖数据库默认值，代码层必须统一负责：

- `created_at`
    
- `updated_at`
    
- `published_at`
    
- `submitted_at`
    
- `sent_at`
    
- `read_at`
    
- `joined_at`
    

以及各类状态初始值、布尔默认值、排序默认值等。

---

# 八、阶段性结论（按当前需求修订）

当前这份数据库设计文档，在约束策略上已经明确采用以下原则：

- 以 **SaaS 多租户** 为根模型
    
- 以 **账号身份与租户成员身份分离** 为基本原则
    
- 以 **组织架构、权限、公告、审批、通知、IM、审计** 为当前核心数据域
    
- **数据库层仅保留主键约束与非空约束**
    
- **除主键和非空外，所有其他约束统一在代码业务层实现**
    
- 后续 AI 编码时，应优先在：
    
    - Pydantic / DTO 输入层
        
    - Service 业务层
        
    - 权限控制层
        
    - 事务与幂等控制层  
        中实现完整约束逻辑，而不是依赖数据库强约束
        

## 对后续开发的直接指导意义

这意味着后续无论是 AI 生成：

- SQLAlchemy 模型
    
- Pydantic Schema
    
- Service 业务逻辑
    
- 权限校验逻辑
    
- 删除逻辑
    
- 状态流转逻辑
    

都应遵循以下统一要求：

### 数据库层

只做：

- 主键
    
- 非空
    

### 代码层

负责：

- 关联存在性校验
    
- 唯一性校验
    
- 多租户归属校验
    
- 权限校验
    
- 数据范围控制
    
- 状态流转
    
- 删除策略
    
- 审计与事件驱动
    
- 默认值填充
    
- 枚举值合法性校验
