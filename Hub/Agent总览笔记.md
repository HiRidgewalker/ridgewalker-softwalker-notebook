## 一、Agent 的核心定义

一个优秀的 Agent，本质上是一个**能够在明确边界内，稳定地理解任务、拆解任务、调用工具执行任务、校验结果并持续推进到完成的智能系统**。

关键词不是"会说"，而是**会做、做对、做稳**。

四个核心维度：

- **理解力**：能正确识别目标、约束、边界、成功条件
- **执行力**：能拆解任务、合理编排工具、稳定推进
- **稳定性**：可预测、可约束、可复现
- **可治理性**：成本可控、行为可控、异常可恢复

## 二、八大核心能力维度

### 1. 目标理解能力

Agent 首先要能正确理解：

- 用户真正要什么
- 任务边界是什么
- 哪些该做，哪些不该做
- 输出标准是什么
- 成功条件是什么

差的 Agent 会立刻开始乱写代码；好的 Agent 会先识别范围、约束、产出形式。

**优秀 Agent 的第一特征，不是做得快，而是"不会一开始就做错方向"。**

### 2. 任务拆解能力

复杂任务几乎都不能一步完成。优秀 Agent 要能把大任务拆成：

- 阶段 → 模块 → 子任务
- 执行顺序与依赖关系

以"开发一个系统"为例，至少要拆成：需求理解、约束识别、数据建模、接口设计、页面设计、权限设计、日志与异常处理、测试策略、部署方案。

不会拆解的 Agent 容易漏做关键步骤、顺序混乱、返工很多。

**把模糊问题结构化的能力。**

### 3. 规划与执行能力

会拆解还不够，还要会执行。需要知道：

- 当前该先做什么
- 哪一步必须依赖前一步
- 哪些可以并行
- 什么时候该停止扩写
- 什么时候该回头修正

即 **plan → act → observe → adjust** 的基本能力。

### 4. 工具使用能力

真正有用的 Agent 几乎一定不是纯聊天模型，而是 **LLM + Tools**。需要知道：

- 什么时候该搜索文档
- 什么时候该读文件 / 查数据库 / 调 API / 跑代码
- 什么时候不该乱调用工具

工具能力的关键是：

- **选对工具、用对时机、拿到结果后会解释、知道结果是否可信**

> 不是"工具越多越强"，而是"工具编排合理"。

### 5. 记忆与上下文管理能力

很多 Agent 失败不是因为模型不聪明，而是**上下文管理太差**。需要管理三类上下文：

- **当前任务上下文**：本轮对话、当前文件、当前目标
- **长期偏好与约束**：用户偏好（专业表达、稳定性、健壮性）、常用技术栈
- **过程状态**：哪些步骤已完成、哪些未完成、当前卡在哪、下一步该继续什么

没有状态感就会重复问同一个问题、忘记之前的约束、做着做着偏题。

**上下文压缩、状态记录、约束继承、阶段记忆**的能力。

### 6. 结果校验与自我纠错能力

这是区分"能跑"和"好用"的关键层。需要至少五种校验：

- **逻辑校验**：前后是否矛盾、是否漏项
- **格式校验**：是否符合指定格式、规范、模板
- **约束校验**：有没有违反用户说过的要求
- **工具结果校验**：返回结果是否为空、是否异常、是否可信
- **业务校验**：结果是否真正解决了用户问题

**会质疑自己的输出。**

### 7. 稳定性与可控性

工程角度最重要的一层。Agent 再聪明，如果结果忽好忽坏，就很难投入使用。需要具备：

- 输出风格稳定
- 遵守边界稳定
- 多轮任务中行为稳定
- 面对异常输入不容易崩
- 对不确定问题会明确说明
- 不会乱编
- 不会擅自扩大任务范围

**可预测、可约束、可复现。**

### 8. 成本意识与效率意识

Agent 不是无限资源的。需要平衡：

- token 成本
- 推理成本
- 工具调用成本
- 响应延迟
- 用户等待体验

成熟 Agent 的平衡策略：

- 简单任务快处理
- 复杂任务深处理
- 高风险任务严校验
- 重复任务模板化

## 三、系统结构（七层）

从工程角度看，优秀 Agent 往往不只是一个 prompt，而是几层组合：

| 层 | 职责 |
| --- | --- |
| **角色层** | 定义它是谁、负责什么、不负责什么（如代码 Agent / 文档 Agent / 数据分析 Agent / 审批流 Agent） |
| **目标层** | 明确输入、输出、成功标准、边界条件 |
| **规划层** | 决定任务如何拆解、如何排序、是否需要中间检查点 |
| **执行层** | 调用模型、工具、函数、数据库、文件系统等 |
| **校验层** | 检查结果质量、完整性、合法性 |
| **记忆层** | 保存偏好、约束、任务状态、历史结论 |
| **安全层** | 防止越权、误操作、胡编、泄露敏感信息 |

> 很多人做 Agent 效果不好，其实只是写了一个"长 prompt"，但没有把 Agent 当系统来设计。

## 五、常见误区

1. **以为 prompt 越长越好** —— 重点是结构清楚、约束明确、优先级明确。
2. **以为模型越强 Agent 就越强** —— 很多时候决定效果的是流程、工具、记忆、校验机制。
3. **以为能回答问题就是 Agent** —— Agent 强调"完成任务"，不是"回答得像懂了"。
4. **以为多智能体一定更强** —— 多 Agent 只有在任务可分工、可校验时才有价值，否则只增加成本。
5. **忽视边界控制** —— 没有边界的 Agent 容易变成"看起来积极，实际不可靠"。

## 六、6 问判断框架

评估一个 Agent 是否优秀，直接看这 6 个问题：

1. 它是否真正理解了目标？
2. 它是否把任务拆清楚了？
3. 它是否会合理调用工具？
4. 它是否会检查自己的结果？
5. 它是否能记住约束并持续推进？
6. 它的结果是否稳定、可控、可复用？

> 只要这 6 点里有 2~3 点很弱，这个 Agent 基本就不算成熟。
